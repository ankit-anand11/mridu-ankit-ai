Summary

Screen 1: IBM API Studio — Test detail, GET/petId  ·  Screen 2: IBM API Connect — API Manager, Paths & Operations detail.

Both inputs are live dev builds from related IBM API management products. 13 findings identified. The most significant are structural Carbon violations shared across both products — custom tree navigation and inconsistent tab variants — creating a cross-product consistency problem for every user navigating between the two tools.

⚠ Image-inferred. All findings are based on visual inspection — no Figma URL or Code Connect data was provided. Token-level violations cannot be confirmed from screenshots alone. One false positive was corrected this session: F1 (Create new assertion button) was confirmed as Carbon Tertiary via the Figma panel.

Carbon Compliance Findings
F2 Left navigation tree — custom implementation in both products Critical image-inferred
Location
Issue & Why it matters
Fix
Critical
● Both screens
Screen 1 — entire left tree panel (APIs, Policy sequences, Tests, Environment, Assertion hierarchy)

Screen 2 — same structure, different custom implementation with ⊕ inline add icons and chevron expand targets
Two different custom tree navigation implementations across two related products. Neither uses Carbon's TreeView component. API Studio uses custom caret icons with a blue left-border selected state. API Connect uses a separate custom pattern.

Carbon's TreeView handles keyboard navigation, expand/collapse, and selected state automatically via $layer-selected-01. Two visually and behaviourally different navigation systems for identical content structures increase maintenance cost and confuse users moving between products.

Carbon TreeView usage →
Replace both custom trees with Carbon TreeView. Remove all custom border/background CSS — $layer-selected-01 is applied automatically.
import { TreeView, TreeNode } from '@carbon/react'; <TreeView label="Explorer"> <TreeNode id="apis" label="APIs" isExpanded> <TreeNode id="api1" label="API 1" /> </TreeNode> <TreeNode id="tests" label="Tests" isExpanded> <TreeNode id="name" label="Test name" selected /> </TreeNode> </TreeView> // Remove custom active state: // .nav-item--active { // border-left: 3px solid #0f62fe; // }
F3 Tabs — two different Carbon variants across the same product suite Critical image-inferred
Location
Issue & Why it matters
Fix
Critical
● Both screens
Screen 1 — tab bar: Parameters / Body / Header / Assertions (line variant)

Screen 2 — top tabs: API Spec / Policy / API Set (contained variant) + nested tabs below: General information / Security / Paths and Operations (line — a second bar on the same screen)
API Studio uses line tabs (underline on active). API Connect uses contained tabs at the top level and nests a second set of line tabs directly below — two tab bars on one screen.

Carbon specifies one Tab variant per product context. Mixing line and contained falsely signals different navigation hierarchies. Carbon does not support nested tab bars.

Carbon Tabs usage →
Align both products to line tabs. Remove contained variant from API Connect. Consolidate the two tab levels on Screen 2 into one.
import { Tabs, TabList, Tab, TabPanels, TabPanel } from '@carbon/react'; <Tabs> <TabList aria-label="API detail sections"> <Tab>Parameters</Tab> <Tab>Body</Tab> <Tab>Assertions</Tab> </TabList> <TabPanels> <TabPanel>...</TabPanel> </TabPanels> </Tabs> // Remove: <Tabs type="contained">

F5 Breadcrumb — current page item is a link on both screens Major image-inferred
Location
Issue & Why it matters
Fix
Major
● Both screens
Screen 1 — "Test 1 / GET/petId" — last item styled as a blue link

Screen 2 — "Projects / jacobson_goldner…" — last item styled as a blue link
The current page item in both breadcrumbs is rendered as a clickable blue link — visually identical to parent items. Carbon requires the current page to be non-interactive, using isCurrentPage with no href.

A clickable current-page item navigates nowhere or reloads the page unexpectedly. Screen readers rely on the semantic distinction to announce the user's current location correctly.

Carbon Breadcrumb usage →
Add isCurrentPage to the last BreadcrumbItem and remove its href. Apply to both products.
import { Breadcrumb, BreadcrumbItem } from '@carbon/react'; <Breadcrumb> <BreadcrumbItem href="/tests"> Test 1 </BreadcrumbItem> <BreadcrumbItem isCurrentPage> GET/petId </BreadcrumbItem> </Breadcrumb>

F7 Active nav item uses custom border instead of $layer-selected-01 Major image-inferred
Location
Issue & Why it matters
Fix
Major
● Screen 1
"Test name" in left nav and "GET/petID" in Outline panel — both show a solid blue left border as selected indicator
A solid #0f62fe left border is used as the selected indicator. Carbon's TreeView selected state uses $layer-selected-01 as a full-row background fill — not a border.

The hardcoded #0f62fe (Blue-60) breaks under theme changes. $layer-selected-01 adapts automatically across White, Gray 10, Gray 90, and Gray 100 themes.
Remove the custom border CSS. Use Carbon TreeNode's selected prop — $layer-selected-01 is applied automatically.
// Remove .nav-item--active { border-left: 3px solid #0f62fe; } // After — Carbon handles selected state <TreeNode id="test-name" label="Test name" selected />
F8 Header background inconsistent between products — possible hardcoded hex Major image-inferred
Location
Issue & Why it matters
Fix
Major
● Both screens
Screen 1 — near-black, consistent with Carbon Gray 100 (#161616)

Screen 2 — visibly lighter dark (~#1a1a1a or custom value)
The two product headers have visibly different dark background shades. At least one — possibly both — is using a hardcoded hex value rather than the Carbon shell token.

A perceptible colour difference in the top navigation bar between two related products signals to users that they are in separate applications. The correct token $background-inverse adapts correctly across all Carbon themes.
Align both headers to the same Carbon shell token. Remove any hardcoded hex background values.
// Before .header { background: #1a1a1a; } // After @use '@carbon/react/scss/theme' as *; .header { background: $background-inverse; }

Minor

Content area — gap above "Path parameters" heading (~40px) differs from gap below heading to the table (~24px)

F10 Page title size inconsistent — ~30px on Screen 1 vs ~22px on Screen 2 Major image-inferred
Location
Issue & Why it matters
Fix
Major
● Both screens
Screen 1 — "GET/petId" — approximately 28–32px, semibold

Screen 2 — "jacobson_goldner_soap_api" — approximately 22–24px, regular weight
Two equivalent page-level titles — the primary heading at the top of each main content area — are rendered at noticeably different sizes and weights across related products.

Page title mismatches make the UI feel unfinished and increase cognitive load for users switching between tools. Carbon's $productive-heading-04 (28px, semibold) is the correct token for page-level titles in productive UIs.
Align both products' page titles to productive-heading-04.
// Before — mismatched // Screen 1: font-size 30px, weight 600 // Screen 2: font-size 22px, weight 400 // After — both products @use '@carbon/react/scss/type' as *; .page-title { @include type-style( 'productive-heading-04' ); }

Accessibility Flags (Carbon pattern level)
F12 Icon-only action buttons missing accessible names — both screens Major image-inferred
Location
Issue & Why it matters
Fix
Major
● Both screens
Screen 1 — assertion section header: ✏ edit + 🔗 link icon buttons

Screen 2 — API title row: ✏ edit + 🗑 delete icon buttons
Four icon-only buttons across both screens have no iconDescription prop. Their purpose is not announced to screen readers or displayed on hover.

Carbon requires all icon-only Buttons to include hasIconOnly and iconDescription. These render as an aria-label and a visible tooltip — without them, keyboard and screen reader users cannot determine what the button does.

Carbon Button accessibility →
Add hasIconOnly and iconDescription to every icon-only Button across both screens.
import { Button } from '@carbon/react'; import { Edit, TrashCan } from '@carbon/icons-react'; <Button kind="ghost" hasIconOnly renderIcon={Edit} iconDescription="Edit assertion" tooltipAlignment="center" /> <Button kind="ghost" hasIconOnly renderIcon={TrashCan} iconDescription="Delete API" tooltipAlignment="center" />

F14 Assertions DataTable missing empty and loading state designs Minor image-inferred
Location
Issue & Why it matters
Fix
Minor
● Screen 1
Assertions DataTable — only the populated state is visible. Screen 2's "No parameters found" empty state with pictogram is the correct model.
No empty state, skeleton loading state, or error state is designed for the assertions table. Without these, developers will build ad-hoc solutions that diverge from Carbon's built-in patterns.

API Connect already gets this right. Replicating the same pattern in API Studio costs minimal effort and ensures users see a consistent experience across both products.
Design and annotate empty and loading states. Use API Connect's "No parameters found" pattern as the model.
import { DataTableSkeleton } from '@carbon/react'; // Loading state {isLoading && ( <DataTableSkeleton columnCount={4} rowCount={3} /> )} // Empty state {!isLoading && rows.length === 0 && ( <p>No assertions found. Create one to get started.</p> )}
