Carbon Compliance Findings
F2 Left navigation tree — custom implementation in both products ● Critical image-inferred
Location
● Both screens
Screen 1 — left tree panel (APIs, Policy sequences, Tests, Environment, Assertion hierarchy)
Screen 2 — left tree panel (same categories, different implementation with ⊕ inline add icons)
Issue
Two different custom tree navigation implementations across two related products. Neither uses Carbon's TreeView component. API Studio uses custom caret icons with a blue left-border selected state. API Connect uses a different custom pattern with chevron expand targets and inline ⊕ add buttons.
Why it matters
Carbon's TreeView handles keyboard navigation, expand/collapse, and selected state automatically using $layer-selected-01 as the background token. A user moving between the two products experiences two visually and behaviourally different navigation systems for identical content structures. Carbon TreeView usage →
Fix
▸ Carbon fix
Replace both custom trees with Carbon TreeView. Remove all custom border/background CSS for selected state — $layer-selected-01 is applied automatically.
import { TreeView, TreeNode } from '@carbon/react'; <TreeView label="Explorer"> <TreeNode id="apis" label="APIs" isExpanded> <TreeNode id="api1" label="API 1" /> </TreeNode> <TreeNode id="tests" label="Tests" isExpanded> <TreeNode id="test-name" label="Test name" selected /> </TreeNode> </TreeView> // Remove — custom active state CSS // .nav-item--active { border-left: 3px solid #0f62fe; } ← delete
F3 Tabs — two different Carbon variants across the same product suite ● Critical image-inferred
Location
● Both screens
Screen 1 — tab bar: Parameters / Body / Header / Assertions (line variant)
Screen 2 — top tabs: API Specification / Policy / API Set (contained variant)
Screen 2 — nested tabs below: General information / Security / Paths and Operations… (line variant — a second tab bar on the same screen)
Issue
API Studio uses line tabs. API Connect uses contained tabs at the top level and nests a second set of line tabs directly below on the same screen. Two different Tab variants in the same product suite, with two tab levels on one screen.
Why it matters
Carbon specifies one Tab variant per product context. Mixing line and contained signals different navigation hierarchies where none exist. Carbon does not support two nested tab bars on one screen. Carbon Tabs usage →
Fix
▸ Carbon fix
Align both products to line tabs. Remove the contained variant from API Connect. Consolidate the two tab levels on Screen 2 into one.
import { Tabs, TabList, Tab, TabPanels, TabPanel } from '@carbon/react'; <Tabs> <TabList aria-label="API detail sections"> <Tab>Parameters</Tab> <Tab>Body</Tab> <Tab>Assertions</Tab> </TabList> <TabPanels><TabPanel>...</TabPanel></TabPanels> </Tabs> // Remove: <Tabs type="contained">
F4 "Refer to existing assertion" — not a Carbon Dropdown, missing label ● Major image-inferred
Location
● Screen 1
Right content panel — wide dropdown field directly below the tab bar
Issue
The dropdown field uses a bottom-border-only style — no box border, no label above the field. This matches neither Carbon Dropdown (full border box) nor Carbon Select. The placeholder text is acting as a label substitute, which Carbon does not permit.
Why it matters
Placeholder text disappears on selection, leaving the field unlabelled. The custom border style breaks under theme changes and lacks Carbon's built-in keyboard accessibility. Carbon Dropdown usage →
Fix
▸ Carbon fix
Replace with Carbon Dropdown. Move the field purpose into titleText — a visible, persistent label above the field.
import { Dropdown } from '@carbon/react'; <Dropdown id="assertion-ref" titleText="Refer to existing assertion" label="Select assertion..." items={assertionItems} itemToString={(item) => (item ? item.label : '')} />
F5 Breadcrumb — current page item is a link on both screens ● Major image-inferred
Location
● Both screens
Screen 1 — "Test 1 / GET/petId" — last item styled as a blue link
Screen 2 — "Projects / jacobson_goldner…" — last item styled as a blue link
Issue
The current page item in both breadcrumbs is rendered as a clickable blue link — visually identical to the parent items. Carbon requires the current page to be non-interactive using the isCurrentPage prop with no href.
Why it matters
A clickable current-page item is confusing — it navigates nowhere or reloads the page. Screen readers rely on the semantic distinction to correctly announce the user's position in the hierarchy. Carbon Breadcrumb usage →
Fix
▸ Carbon fix
Add isCurrentPage to the last BreadcrumbItem and remove its href. Apply to both products.
import { Breadcrumb, BreadcrumbItem } from '@carbon/react'; <Breadcrumb> <BreadcrumbItem href="/tests">Test 1</BreadcrumbItem> <BreadcrumbItem isCurrentPage>GET/petId</BreadcrumbItem> </Breadcrumb>
F6 "Get Started" floating card — not a Carbon component ● Major image-inferred
Location
● Screen 2
Bottom-right corner — white floating card with "Get Started" label and ✕ dismiss button
Issue
A custom position: fixed floating card is used for onboarding guidance. Carbon has no floating onboarding card pattern. No visible focus trap or keyboard dismiss affordance.
Why it matters
Custom overlay elements inherit none of Carbon's focus management, theme token support, or accessibility behaviours. Without a focus trap, keyboard users cannot reliably reach or dismiss the card. Carbon Notification usage →
Fix
▸ Carbon fix
Replace with Carbon ActionableNotification for a persistent message, or IBM Products Coachmark for guided onboarding.
// Option A — ActionableNotification import { ActionableNotification } from '@carbon/react'; <ActionableNotification kind="info" title="Get started" subtitle="Explore the API Manager features." actionButtonLabel="Learn more" onClose={() => setVisible(false)} /> // Option B — IBM Products Coachmark (guided tour) import { Coachmark } from '@carbon/ibm-products';
Token & Spacing Findings
F7 Active nav item uses custom left border instead of $layer-selected-01 ● Major image-inferred
Location
● Screen 1
"Test name" active item in left nav and "GET/petID" in Outline panel — both show a solid blue left border
Issue
A solid #0f62fe left border is used as the selected indicator. Carbon's selected state for TreeView items uses $layer-selected-01 as a full-row background fill — not a border.
Why it matters
The hardcoded #0f62fe value breaks under theme changes. $layer-selected-01 adapts automatically across White, Gray 10, Gray 90, and Gray 100 themes.
Fix
▸ Carbon fix
Remove the custom border CSS. Use Carbon TreeNode's selected prop — $layer-selected-01 is applied automatically.
// Remove .nav-item--active { border-left: 3px solid #0f62fe; } // After — Carbon handles selected state <TreeNode id="test-name" label="Test name" selected />
F8 Header background inconsistent between products — possible hardcoded hex ● Major image-inferred
Location
● Both screens
Screen 1 top bar — near-black, consistent with Carbon Gray 100 (#161616)
Screen 2 top bar — visibly lighter dark (~#1a1a1a or custom)
Issue
The two product headers have visibly different dark background shades. At least one — possibly both — is using a hardcoded hex value rather than the Carbon shell header token.
Why it matters
A perceptible colour difference in the top navigation bar between two related products signals to users that they are in separate applications. The correct token is $background-inverse, which adapts correctly across all Carbon themes.
Fix
▸ Carbon fix
Align both headers to the same Carbon shell token. Remove any hardcoded hex background values.
// Before .header { background: #1a1a1a; } // After @use '@carbon/react/scss/theme' as *; .header { background: $background-inverse; }
F9 Vertical spacing between sections is inconsistent ● Minor image-inferred
Location
● Screen 2
Content area — gap above "Path parameters" heading (~40px) differs from gap below it to the table (~24px)
Issue
Section gaps mix $spacing-08 (40px) and $spacing-06 (24px) within the same screen, creating an uneven vertical rhythm.
Why it matters
Inconsistent spacing creates visual noise that makes the page harder to scan. A single consistent token produces a calm, readable layout.
Fix
▸ Carbon fix
Pick one section-gap token and apply it consistently. $spacing-07 (32px) is recommended.
@use '@carbon/react/scss/spacing' as *; .page-section + .page-section { margin-top: $spacing-07; } .section-heading { margin-bottom: $spacing-05; }
Typography Findings
F10 Page title size inconsistent — ~30px on Screen 1 vs ~22px on Screen 2 ● Major image-inferred
Location
● Both screens
Screen 1 — h1 "GET/petId" — approximately 28–32px, semibold
Screen 2 — h1 "jacobson_goldner_soap_api" — approximately 22–24px, regular weight
Issue
Two equivalent page-level titles — the primary heading at the top of each screen's main content area — are rendered at noticeably different sizes and weights across related products.
Why it matters
Page title mismatches make the UI feel unfinished and increase cognitive load for users switching between tools. Carbon's $productive-heading-04 (28px, semibold) is the correct token for page-level titles in productive UIs.
Fix
▸ Carbon fix
Align both products' page titles to productive-heading-04.
// Before — mismatched .page-title { font-size: 30px; font-weight: 600; } // Screen 1 .page-title { font-size: 22px; font-weight: 400; } // Screen 2 // After — both products @use '@carbon/react/scss/type' as *; .page-title { @include type-style('productive-heading-04'); }
F11 DataTable column headers appear lighter than Carbon's 600 weight ● Minor image-inferred
Location
● Both screens
Screen 1 — table header row: Name / Key / Action / Value
Screen 2 — table header row: Name / Located in / Ref name
Issue
Column header text appears at approximately medium weight (~500) rather than the semibold (600) specified by Carbon's $productive-heading-01 token. A CSS override may be reducing the font weight.
Why it matters
Column headers at correct weight create a clear distinction from data rows — a key scannability cue in data-dense tables. Reduced weight flattens this contrast.
Fix
▸ Carbon fix
Remove any font-weight override on table header labels. Carbon's DataTable applies $productive-heading-01 (600 weight) automatically.
// Remove any override like this: .cds--table-header-label { font-weight: 400; } // ← delete
Accessibility Flags (Carbon pattern level)
F12 Icon-only action buttons missing accessible names — both screens ● Major image-inferred
Location
● Both screens
Screen 1 — assertion section header: ✏ edit + 🔗 link icon buttons
Screen 2 — API title row: ✏ edit + 🗑 delete icon buttons
Issue
Four icon-only buttons across both screens have no iconDescription prop. The purpose of these controls is not announced to screen readers or shown on hover.
Why it matters
Carbon requires all icon-only Buttons to include hasIconOnly and iconDescription. These render as an aria-label and a visible tooltip — without them, keyboard and screen reader users cannot determine what the button does. Carbon Button accessibility →
Fix
▸ Carbon fix
Add hasIconOnly and iconDescription to every icon-only Button across both screens.
import { Button } from '@carbon/react'; import { Edit, TrashCan } from '@carbon/icons-react'; <Button kind="ghost" hasIconOnly renderIcon={Edit} iconDescription="Edit assertion" tooltipAlignment="center" /> <Button kind="ghost" hasIconOnly renderIcon={TrashCan} iconDescription="Delete API" tooltipAlignment="center" />
F13 Tooltip ⓘ trigger next to "Use custom endpoint" has no accessible name ● Minor image-inferred
Location
● Screen 1
Content area — ⓘ icon immediately after the "Use custom endpoint" toggle label
Issue
The toggle label placement is correct per Carbon. The ⓘ tooltip trigger has no aria-label — its purpose cannot be announced to a screen reader.
Why it matters
Screen readers announce this as an unnamed interactive element, which fails Carbon's accessible name requirement for interactive controls.
Fix
▸ Carbon fix
Add aria-label to the tooltip trigger describing what it explains.
import { Tooltip } from '@carbon/react'; import { Information } from '@carbon/icons-react'; <Tooltip description="Overrides the default API base URL."> <button type="button"> <Information aria-label="More information about custom endpoint" /> </button> </Tooltip>

Mechanical WCAG checks (contrast ratios, tab order, screen reader output) are out of scope. Use IBM Equal Access Checker for those.

F14 Assertions DataTable missing empty and loading state designs ● Minor image-inferred
Location
● Screen 1
Assertions DataTable — only the populated state is visible. Screen 2's "No parameters found" empty state (with pictogram) is the correct model to follow.
Issue
No empty state, skeleton loading state, or error state is designed for the assertions table. Without these, developers will build ad-hoc solutions that diverge from Carbon's built-in patterns.
Why it matters
API Connect already gets this right. Replicating the same pattern in API Studio costs minimal effort and ensures users see a consistent experience across both products.
Fix
▸ Carbon fix
Design and annotate empty and loading states. Use API Connect's "No parameters found" pattern as the model.
// Loading state import { DataTableSkeleton } from '@carbon/react'; {isLoading && <DataTableSkeleton columnCount={4} rowCount={3} />} // Empty state {!isLoading && rows.length === 0 && ( <p>No assertions found. Create one to get started.</p> )}
