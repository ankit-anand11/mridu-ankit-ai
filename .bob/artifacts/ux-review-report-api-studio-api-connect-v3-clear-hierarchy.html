Carbon Compliance Findings
F2 Left navigation tree — custom implementation in both products ● Critical image-inferred
Location
● Both screens
Screen 1 — entire left tree panel (APIs, Policy sequences, Tests, Environment, Assertion hierarchy)
Screen 2 — entire left tree panel (same categories, different implementation with ⊕ inline add icons)
Issue
Two different custom tree navigation implementations across two related products. Neither uses Carbon's TreeView component. API Studio uses custom caret icons with a blue left-border selected state. API Connect uses a different custom pattern with chevron expand targets and inline ⊕ add buttons.
Why it matters
Carbon's TreeView handles keyboard navigation, expand/collapse, and selected state automatically using $layer-selected-01 as the background token. Custom implementations break these behaviours and will diverge further from each other over time, increasing maintenance cost. A user moving between the two products experiences two visually and behaviourally different navigation systems for identical content structures. Carbon TreeView usage →
Fix
Replace both custom trees with Carbon TreeView. Remove all custom border/background CSS for selected state — Carbon applies $layer-selected-01 automatically.
// After — same implementation for both products import { TreeView, TreeNode } from '@carbon/react'; <TreeView label="Explorer"> <TreeNode id="apis" label="APIs" isExpanded> <TreeNode id="api1" label="API 1" /> </TreeNode> <TreeNode id="tests" label="Tests" isExpanded> <TreeNode id="test-name" label="Test name" selected /> </TreeNode> </TreeView> // Remove — custom active state CSS // .nav-item--active { border-left: 3px solid #0f62fe; } ← delete
F3 Tabs — two different Carbon variants used across the same product suite ● Critical image-inferred
Location
● Both screens
Screen 1 — horizontal tab bar: Parameters / Body / Header / Assertions / Conditions (line variant)
Screen 2 — top tabs: API Specification / Policy / API Set (contained variant)
Screen 2 — nested tabs below: General information / Security / Paths and Operations… (line variant — a second tab bar on the same screen)
Issue
API Studio uses line tabs (underline on active). API Connect uses contained tabs at the top level (filled background on active) and then nests a second set of line tabs directly below on the same screen. Two different Tab variants are in use across the same product suite, and two tab bars are nested on one screen.
Why it matters
Carbon's usage guideline specifies one Tab variant per product context. Mixing line and contained creates visual inconsistency that signals different navigation hierarchies — but these screens serve equivalent purposes. Nested tab bars compound the problem: Carbon does not support two tab levels on one screen. Carbon Tabs usage →
Fix
Align both products to line tabs (the Carbon default for productive UIs). Remove the contained variant from API Connect. Consolidate the two tab levels on Screen 2 into one.
// Consistent across both products import { Tabs, TabList, Tab, TabPanels, TabPanel } from '@carbon/react'; <Tabs> <TabList aria-label="API detail sections"> <Tab>Parameters</Tab> <Tab>Body</Tab> <Tab>Assertions</Tab> </TabList> <TabPanels><TabPanel>...</TabPanel></TabPanels> </Tabs> // Remove: <Tabs type="contained"> — not appropriate here
F4 "Refer to existing assertion" — not a Carbon Dropdown, missing label ● Major image-inferred
Location
● Screen 1
Right content panel — wide dropdown field directly below the tab bar
Issue
The dropdown field uses a bottom-border-only style — no box border, no label above the field. This matches neither Carbon Dropdown (full border box) nor Carbon Select. The placeholder text "Refer to existing assertion" is acting as a label substitute, which Carbon does not permit.
Why it matters
Carbon requires a visible titleText label above every Dropdown or Select — placeholder text disappears on selection, leaving the field unlabelled. The custom border style will break under theme changes and is not keyboard-accessible without Carbon's built-in focus management. Carbon Dropdown usage →
Fix
Replace with Carbon Dropdown. Move the field purpose into titleText (visible label above the field).
import { Dropdown } from '@carbon/react'; <Dropdown id="assertion-ref" titleText="Refer to existing assertion" label="Select assertion..." items={assertionItems} itemToString={(item) => (item ? item.label : '')} />
F5 Breadcrumb — current page item is a link on both screens ● Major image-inferred
Location
● Both screens
Screen 1 — breadcrumb: "Test 1 / GET/petId" — last item styled as a blue link
Screen 2 — breadcrumb: "Projects / jacobson_goldner…" — last item styled as a blue link
Issue
The current page item in both breadcrumbs is rendered as a blue clickable link — visually identical to the parent items. Carbon requires the current page to be non-interactive and visually distinct, using the isCurrentPage prop with no href.
Why it matters
A clickable current-page item is confusing — clicking it navigates nowhere useful or refreshes the page unexpectedly. Screen readers rely on the semantic distinction to correctly announce the user's current location in the hierarchy. Carbon Breadcrumb usage →
Fix
Add isCurrentPage to the last BreadcrumbItem and remove its href. Apply the same fix to both products.
import { Breadcrumb, BreadcrumbItem } from '@carbon/react'; <Breadcrumb> <BreadcrumbItem href="/tests">Test 1</BreadcrumbItem> <BreadcrumbItem isCurrentPage>GET/petId</BreadcrumbItem> </Breadcrumb>
F6 "Get Started" floating card — not a Carbon component ● Major image-inferred
Location
● Screen 2
Bottom-right corner — white floating card with "Get Started" label and ✕ dismiss button
Issue
A custom position: fixed floating card is used for onboarding guidance. Carbon has no floating onboarding card pattern. The element has no visible focus trap and no keyboard dismiss affordance visible in the screenshot.
Why it matters
Custom overlay elements that are not Carbon components inherit none of Carbon's focus management, theme token support, or accessibility behaviours. Without a focus trap, keyboard users cannot reliably reach or dismiss the card. Carbon Notification usage →
Fix
Replace with Carbon ActionableNotification for a persistent inline message, or IBM Products Coachmark for guided onboarding.
// Option A — ActionableNotification import { ActionableNotification } from '@carbon/react'; <ActionableNotification kind="info" title="Get started" subtitle="Explore the API Manager features." actionButtonLabel="Learn more" onClose={() => setVisible(false)} /> // Option B — IBM Products Coachmark (guided tour) import { Coachmark } from '@carbon/ibm-products';
Token & Spacing Findings
F7 Active nav item uses custom left border instead of $layer-selected-01 ● Major image-inferred
Location
● Screen 1
Left nav — "Test name" active item and "GET/petID" in the Outline panel — both show a solid blue left border as the selected indicator
Issue
A solid #0f62fe left border is used as the selected/active state indicator. Carbon's selected state for TreeView and SideNav items uses $layer-selected-01 as a full-row background fill — not a border.
Why it matters
The custom border pattern will break when the theme changes — #0f62fe is Blue-60 hardcoded, not a semantic token. The $layer-selected-01 token adapts correctly to White, Gray 10, Gray 90, and Gray 100 themes automatically.
Fix
Remove the custom border CSS. Use Carbon TreeNode's built-in selected prop — $layer-selected-01 is applied automatically.
// Before — remove this .nav-item--active { border-left: 3px solid #0f62fe; } // After <TreeNode id="test-name" label="Test name" selected /> // $layer-selected-01 applied automatically — theme-safe
F8 Header background colour inconsistent between products — possible hardcoded hex ● Major image-inferred
Location
● Both screens
Screen 1 top bar — near-black, consistent with Carbon Gray 100 (#161616)
Screen 2 top bar — visibly lighter dark, approx #1a1a1a or custom — different to Screen 1
Issue
The two product headers have visibly different dark background shades. At least one — and possibly both — is using a hardcoded hex value rather than the Carbon shell header token.
Why it matters
A perceptible colour difference in the top navigation bar between two products in the same suite signals to users that they are in different applications — even if the functionality is related. The correct token is $background-inverse or $shell-header-bg-01; both adapt correctly to theme changes.
Fix
Align both headers to the same Carbon shell token. Remove any hardcoded hex background values.
// Before .header { background: #1a1a1a; } // ← hardcoded // After @use '@carbon/react/scss/theme' as *; .header { background: $background-inverse; }
F9 Vertical spacing between sections is inconsistent ● Minor image-inferred
Location
● Screen 2
Content area — gap above "Path parameters" heading (~40px) vs gap below it to the table (~24px)
Issue
The vertical gaps between sections within the same screen appear to mix $spacing-08 (40px) and $spacing-06 (24px), creating an uneven vertical rhythm.
Why it matters
Inconsistent spacing creates visual noise that makes pages feel unpolished and harder to scan. Consistent use of a single section-gap token produces a calm, readable layout.
Fix
Pick one section-gap token and apply it consistently. $spacing-07 (32px) is a good default for page-level section gaps.
@use '@carbon/react/scss/spacing' as *; .page-section + .page-section { margin-top: $spacing-07; } .section-heading { margin-bottom: $spacing-05; }
Typography Findings
F10 Page title size inconsistent — ~30px on Screen 1 vs ~22px on Screen 2 ● Major image-inferred
Location
● Both screens
Screen 1 — h1 "GET/petId" — approximately 28–32px, semibold
Screen 2 — h1 "jacobson_goldner_soap_api" — approximately 22–24px, regular weight
Issue
Two equivalent page-level titles — the primary heading at the top of the main content area — are rendered at noticeably different sizes and weights across two related products.
Why it matters
Page titles establish the visual hierarchy of a screen. A mismatch in size and weight between equivalent titles in the same product suite makes the UI feel unfinished and increases cognitive load for users switching between tools. The Carbon token $productive-heading-04 (28px, semibold) is the correct choice for page-level titles in productive UIs.
Fix
Align both product page titles to productive-heading-04. Apply the same type-style mixin in both codebases.
// Before — mismatched .page-title { font-size: 30px; font-weight: 600; } // Screen 1 .page-title { font-size: 22px; font-weight: 400; } // Screen 2 // After — both products @use '@carbon/react/scss/type' as *; .page-title { @include type-style('productive-heading-04'); }
F11 DataTable column headers appear lighter than Carbon's 600 weight ● Minor image-inferred
Location
● Both screens
Screen 1 — table header row: Name / Key / Action / Value
Screen 2 — table header row: Name / Located in / Ref name
Issue
Column header text appears at approximately medium weight (~500) rather than the semibold (600) specified by Carbon's $productive-heading-01 token. A CSS override may be reducing the font weight on table header labels.
Why it matters
Column headers at the correct weight create a clear distinction between header and data rows — a key scannability cue in data-dense tables. Reduced weight flattens this contrast.
Fix
Remove any font-weight override on table header labels. Carbon's DataTable applies $productive-heading-01 (600 weight) automatically.
// Remove any override like this: .cds--table-header-label { font-weight: 400; } // ← delete // Carbon DataTable applies correct weight automatically import { DataTable, Table, TableHead, TableRow, TableHeader } from '@carbon/react';
Accessibility Flags (Carbon pattern level)
F12 Icon-only action buttons missing accessible names — both screens ● Major image-inferred
Location
● Both screens
Screen 1 — assertion section header: ✏ edit icon + 🔗 link icon (top-right of assertion row)
Screen 2 — API title row: ✏ edit icon + 🗑 delete icon (inline with the page title)
Issue
Four icon-only buttons across both screens have no visible label and no iconDescription prop. The purpose of these controls is not announced to screen readers.
Why it matters
Carbon requires all icon-only Buttons to include hasIconOnly and iconDescription. These props render as an aria-label and a visible tooltip on hover — without them, keyboard and screen reader users cannot determine what the button does. This is a Carbon accessibility pattern requirement, not just a WCAG recommendation. Carbon Button accessibility →
Fix
Add hasIconOnly and iconDescription to every icon-only Button. Apply to all four instances across both screens.
import { Button } from '@carbon/react'; import { Edit, TrashCan, Link } from '@carbon/icons-react'; <Button kind="ghost" hasIconOnly renderIcon={Edit} iconDescription="Edit assertion" tooltipAlignment="center" /> <Button kind="ghost" hasIconOnly renderIcon={TrashCan} iconDescription="Delete API" tooltipAlignment="center" />
F13 Tooltip ⓘ icon next to "Use custom endpoint" has no accessible name ● Minor image-inferred
Location
● Screen 1
Content area — ⓘ information icon immediately after the "Use custom endpoint" toggle label
Issue
The toggle label and placement are correct per Carbon. However the ⓘ tooltip trigger icon has no aria-label — its purpose cannot be announced to a screen reader.
Why it matters
Screen readers will announce this as an unnamed button, which is confusing to assistive technology users and fails Carbon's accessible name pattern requirement for interactive controls.
Fix
Add aria-label to the tooltip trigger button describing what the tooltip explains.
import { Toggle, Tooltip } from '@carbon/react'; import { Information } from '@carbon/icons-react'; <Toggle labelText="Use custom endpoint" id="custom-ep" /> <Tooltip description="Overrides the default API base URL."> <button type="button"> <Information aria-label="More information about custom endpoint" /> </button> </Tooltip>

Mechanical WCAG checks (contrast ratios, tab order, screen reader output) are out of scope. Use IBM Equal Access Checker for those.

F14 Assertions DataTable missing empty and loading state designs ● Minor image-inferred
Location
● Screen 1
Assertions DataTable — only the populated state is visible in the design
Issue
No empty state, skeleton loading state, or error state is designed for the assertions table. Screen 2 (API Connect) correctly shows a "No parameters found" empty state with a pictogram — Screen 1 should follow the same pattern.
Why it matters
Without these states designed, developers will build ad-hoc solutions that diverge from Carbon's built-in DataTableSkeleton and empty state patterns. The API Connect empty state is already the correct model — replicating it in Screen 1 costs minimal effort and ensures consistency.
Fix
Design and annotate empty and loading states. Use API Connect's "No parameters found" pattern as the model for the empty state.
// Loading state import { DataTableSkeleton } from '@carbon/react'; {isLoading && <DataTableSkeleton columnCount={4} rowCount={3} />} // Empty state {!isLoading && rows.length === 0 && ( <p>No assertions found. Create one to get started.</p> )}
