01 · The problem

Carbon compliance has no enforcement layer

Developers and designers want to build correctly. The problem is that there is no way to verify they have — until something breaks.

What teams experience today

Spacing is hard-coded
Developers read spacing from Figma inspect and write padding: 16px instead of $spacing-05. Theme switches break silently.
Tokens are bypassed
Hex values are copied from Figma inspect and hard-coded into CSS. The screen looks correct — but fails on dark mode or theme switch.
Wrong components inherited
When Bob generates UI in a repo with legacy components, it reuses them without warning — unless the developer explicitly says "use Carbon".
No review gate
Non-compliant code can merge with no accountability. Issues surface in QA post-merge — or never at all.
"If they are really using the Carbon component, are they really using the tokens? No one has any idea. So that gap is still there."
Senthil Kumaran Pattabiraman · Tech Lead, IBM API (webMethods)
"Unless you approve, it can't get merged — so they will get pulled up for it. So they will do it fast so that you review it."
Diya Susan Joseph · Designer, IBM API Management (webMethods)

Top developer findings (2 of 3 reported)

Critical

Token compliance is invisible

A screen can look correct while the code uses hardcoded hex values. No one can tell from a screenshot, a video, or a visual review.

Critical

No formal review gate

Non-compliant code merges with no accountability. Issues surface in QA post-merge — or never. Without a gate, teams have no shared compliance artefact.

Major

Bob inherits legacy components

When Bob generates UI in a repo with legacy components, it reuses them without warning — compliance is opt-in, not enforced by default.

Major

Custom component maintenance debt

Pre-Carbon components are now orphaned. No Carbon team ownership, full maintenance burden on the product team. Accessibility failures are the team's liability.

Desired

Compliance check before PR

A self-service gate developers control — run it themselves after their own visual check, before raising a PR. Not a QA catch, not a designer chase.

Desired

Figma vs. implementation delta

A structured comparison between what was designed and what was actually built — with a report that becomes a Jira ticket developers can take straight to Bob.

Six confirmed market gaps

Derived from the comparison matrix. No tool surveyed addresses any of these — especially not for Carbon.

G1

Hardcoded values in code

No tool detects hex/px values in a developer's branch and maps them to the correct Carbon token.

G2

Non-Carbon component detection

No tool flags a PrimeNG or legacy component in a codebase and names the Carbon/Web Component replacement.

G3

Carbon-specific PR gate

Chromatic blocks on visual regression only. No tool blocks merge on Carbon compliance — components, tokens, spacing.

G4

Figma vs. implementation delta

No tool compares what was designed in Figma against what was implemented in the branch.

G5

Auto-create Jira ticket

No tool turns compliance findings into a Jira ticket with structured acceptance criteria.

G6

Carbon as the rule set

All five tools are design-system-agnostic. Every team must configure their own rules. No tool ships Carbon-aware.

04 · The solution

UX Reviewer closes all six gaps — inside Bob, no procurement needed

Not a linter. Not a visual regression tool. Not a documentation platform. A Carbon compliance workflow — from Figma frame to code branch to Jira ticket — delivered as a conversation in Bob.

0
New tools required. Everything runs through Bob infrastructure IBM teams already have.
0
Procurement needed. Carbon MCP, Figma MCP, and Jira MCP are available to all IBM teams today.
Live
Carbon MCP rule source — maintained by the Carbon team, updated with every release, never stale.

Six capabilities. One workflow.

Each capability uses IBM infrastructure that already exists. Everything in Phase 1 is available today.

C1 · Phase 1

Figma frame compliance

Identify Carbon vs. custom components. Flag wrong variants. Name the correct Carbon alternative — including Web Components for Angular teams.

Figma MCP: get_code_connect_map
Carbon MCP: docs_search
C2 · Phase 1

Token audit (Figma)

Detect hardcoded hex and px values per Figma node. Name the Carbon token that should replace each one and explain the semantic context.

Figma MCP: get_variable_defs
Carbon MCP: docs_search
C3 · Phase 1

Code compliance (branch)

Scan source imports and SCSS for non-Carbon components and hardcoded values. Suggest Carbon and Web Component replacements, file by file.

Bob file tools + Carbon MCP
stylelint-plugin-carbon-tokens
C4 · Phase 1

Figma vs. implementation delta

Compare a Figma screenshot against a user-supplied implementation screenshot. Carbon-aware interpretation of every visual difference found.

Figma MCP: get_screenshot
Claude vision + Carbon MCP
C5 · Phase 1

Auto-create Jira ticket

When findings exist, create a structured Jira ticket — title, description, severity-ranked findings, acceptance criteria, labels, assignee — automatically.

Jira MCP (already a Bob skill)

05 · Next steps

Three steps before sprint 1

The Phase 1 experience is available to every IBM team on Bob today. The only work needed is validation and pilot setup.

01

Validate the report format

  • 30-min session with one designer (Diya or Animesh)
  • 30-min session with one developer (Senthil or Sahana)
  • Show a sample report generated from a real Figma frame
  • Confirm finding categories and severity definitions
02

Set up the pilot

  • Set up Code Connect on a pilot Figma frame (API team)
  • Confirm Jira board ID, label taxonomy, assignee mapping
  • Build the Bob skill scaffold and report template
  • Confirm skill trigger — natural language or /ux-review
03

Run a live demo

  • Generate a real compliance report on API team's current sprint work
  • Show Senthil the Jira ticket output end-to-end
  • Iterate on report format before opening to other teams
  • Document the pilot outcome as a replicable model for other teams

Open questions before sprint 1

Which team is the pilot?
Senthil's API team is the strongest candidate — highest Carbon maturity, most articulate about what the tool should do, already on Bob.
Frames with no Code Connect?
Hariharan's team has no Code Connect. Need a graceful fallback — image-based identification or a setup guide.
Skill trigger method?
Natural language ("review this frame") or slash command (/ux-review)? This affects the skill description and example prompts.
What does "fixed" look like?
Acceptance criteria need to be specific enough for a developer to close them without re-review. A few concrete examples need to be written and validated.
